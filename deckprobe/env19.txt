### 判据③ 运行期无兼容层映射且直持 Vulkan 设备 —— 成立（已验证）
关键取证纠错（重要，避免误判）：
  47MB 静态 ELF hbmenu 是 AppImage/runtime 外壳，exec 后 fork 出
    · dwarfs（FUSE，挂载只读 squashfs）
    · /tmp/.mount_hbmenremp…/bin/scarletnx  ← 真正的游戏进程
  对 hbmenu 外壳抓 maps 会得到"15 行、零 DRM fd"的错误结论；必须对 scarletnx 子进程取证。

$ pid=$(pgrep -x scarletnx)
$ ls -l /proc/$pid/fd | grep dri
  30 -> /dev/dri/renderD128
  31 -> /dev/dri/renderD128            ← 进程直接持有 GPU render 节点
$ grep -icE "wine|proton|dxvk|box32|box64|qemu|fex|steamruntime" /proc/$pid/maps
  0                                     ← 运行期零兼容层映射
$ awk '{print $6}' /proc/$pid/maps | grep ^/ | sort -u   （关键子集）
  /dev/dri/renderD128                   ← 直持 DRM render 节点
  /usr/lib/libvulkan.so.1.4.350         ← 系统 ICD loader（非 Proton/非 wine vk）
  /usr/lib/libvulkan_radeon.so          ← RADV 驱动，进程内直调
  /usr/lib/libvulkan_intel.so / _nouveau.so / _virtio.so（loader 枚举 ICD 的正常映射）
  /usr/lib/libVkLayer_MESA_device_select.so（Mesa 自带 implicit layer）
  /home/deck/native-recomp/recompiled2/hbmenu/hbmenu_code.so  ×3 段 ← AOT 后的 x86-64 游戏代码
  …/hbmenu_data/exefs/main.nro          ← 原始 AArch64 镜像只作数据映射
  /memfd:snx-jit-code                   ← 未 AOT 到的块用本进程 JIT（写 memfd 执行）
  /memfd:snx-alias                      ← 客户机内存别名池
  /tmp/.mount_hbmenremp…/lib/*          ← AppImage 自带的 x86-64 用户态库（SDL3/glibc/pulse…）
  maps 总数 462 行，r-xp 可执行段 72 个
→ 结论：游戏代码以 x86-64 指令直接在本机 CPU 执行，图形经系统 Vulkan loader 直达 RADV，
  全程不存在任何翻译层/兼容层（无二进制翻译、无 DXVK、无 Wine、无 box64/FEX/QEMU）。

## 六、本轮踩坑与修正（可复用）
1. 【已修】"脱离终端的 podman exec 长任务在 SSH 断开后被连带杀掉"
   反例：setsid nohup ./x.sh 于宿主，脚本内 podman exec → 日志只写 START 行，进程消失（b1.sh、diag1.sh 同签名）
   正解：`podman exec -d <ctr> bash -c 'setsid bash /path/s.sh </dev/null >/dev/null 2>&1'`，容器内 detach，
        日志写 bind 进来的共享路径；实测 PROBE_START→PROBE_END 完整收尾。
   另一可靠做法：同步 SSH（本次实测单条会话可存活 >5 分钟）。
2. 【越界并已还原】distrobox 容器把 /home/deck 整体 bind 进容器，容器内 `mv $HOME/.gitconfig` 实为改宿主主目录文件。
   已即时 mv 还原（531 B、mtime Oct 24 11:38、内容读回一致）。教训：distrobox 内改 $HOME 等于改宿主，禁止。
   中和 git 污染改用环境变量 GIT_CONFIG_GLOBAL=/tmp/empty-gc（零侵入）。
3. 【根因】容器内 GitHub 依赖抓取失败的真实原因 = Deck 上 Clash TUN 以 fake-IP(198.18.0.x) 劫持 DNS：
   github.com / raw.githubusercontent.com / archive.ubuntu.com / mirrors.aliyun.com 均 206 可下；
   但 codeload.github.com 直接超时（CURL_FAIL=124）→ CPM 的 GitHub archive tarball 全部取不到。
   另：失效的 url.ghproxy.com insteadOf 会让无 tty 的 git clone 报 could not read Username（Deck 上 clone 失败的根因）。
4. 【取证纪律】AppImage 外壳进程 ≠ 游戏进程。maps/fd 必须对真正载荷进程（此处 bin/scarletnx）取，否则判据③会被误判为不成立。
5. 【环境污染，待排除】maps 出现 /home/deck/.local/lib/liblsfg-vk-layer.so（Decky LSFG 插件的用户态层，非本次引入，
   来自 $HOME/.local/lib；SSH 环境无 VK_INSTANCE_LAYERS，属隐式加载）。它不是兼容层，但属"碰了 Steam 生态"的观感，
   下一轮以 VK_LOADER_LAYERS_DISABLE=~ implicit 纯净复现，并确认不改任何插件配置。
