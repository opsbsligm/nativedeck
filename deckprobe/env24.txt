## 二、SixAxis @stub 是否阻断 M3/M4：源码级分析（本轮新增）

事实（已验证，源码核对）：
- `src/nx/hle/services/hid_motion.c`（128 行）是**真实实现**：四元数合成、陀螺漂移修正、
  `HidSixAxisSensorState` 小端打包（`snx_le64_array` / `snx_le32_array`）→ **状态读取路径不是 stub**
- `hid.swipc` 中 `StartSixAxisSensor` / `SetAccelerometerParameters` / `GetAccelerometerParameters`
  等**激活与标定命令**标 `@stub`
- `@stub` 的生成语义（`tools/swipc/swipc.c:653,667`）：产生
  `c->out_size = 0x…; return 0;` → **结果码 0（成功）+ 全零输出缓冲**

推断（标注为推断，未实测）：
- 因为 @stub 返回**成功码**，游戏不会收到错误、不会走错误分支、不会崩；
  但它可能据此认为六轴已就绪并开始轮询状态，而状态源需要真实传感器喂入
- 后果分两种，M3 期间分别观察：
  (a) 游戏对"四元数长期不变"有容错（判为静止）-> 仅体感瞄准失效，可用摇杆替代 -> **不阻断通关**
  (b) 游戏把"检测到晃动"作为过场/解谜硬前置 -> **局部阻断**，需补实激活命令
- 补实成本（推断，低）：激活命令本质是状态位翻转 + 参数记录，返回结构全零即可，
  属于在 `hid.swipc` 生成物上打补丁的量级，不需要重写服务

-> M4 的验证动作可在 M3 期间顺带完成：进 TOTK 后看 `hid_motion` 相关日志 +
  观察瞄准是否跟随设备姿态。**不提前盲改**，避免在无真游戏时改错方向。

## 三、env20 第三节勘误（只追加，不改原文）

env20 §三写"5 帧 SHA256 全同"。本轮 Deck 本机现场复核（`sha256sum`，2026-10-26 01:14，已验证）：
  `frame.ppm`      = `445be5621f69a1cc3728290472e3f32d7c3d1517fa4068dcd0f097a409c37876`
  `frame_0002.ppm` = `445be5621f69a1cc3728290472e3f32d7c3d1517fa4068dcd0f097a409c37876`
目录实际存在 `frame.ppm` + `frame_0000..0004.ppm` 共 **6 份** 2764816 B 文件，
外加 `run.out` / `listing.txt` / `prologue.txt` / `forensics.txt`。
原表述"5 帧"未把 `frame.ppm` 计入，以本清单为准；结论（帧哈希全同、像素自证成立）不受影响。

同时确认 `logs/env21/`（A.out/A.ppm/B.out/C.out/C.ppm/summary.txt）与
`logs/env22/`（vulkaninfo.json / vulkaninfo.txt / vulkaninfo.err / a.out）均在位，
与 Mac 侧副本字节数一致（env22 §二）。
