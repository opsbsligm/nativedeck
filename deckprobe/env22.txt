## 一、为什么要做这一轮

M2 的关键问题是"这台机器的 Vulkan 驱动到底能不能撑起 TOTK 级别的移植"。
Deck 主机 `command -v vulkaninfo` **不存在**（env21 第四节已记录），因此：
  路线 A：容器内装 vulkan-tools（apt，容器态，不写 rootfs）→ 本轮
  路线 B：从 ScarletNX 运行日志反推 → 覆盖率不足，作为交叉验证
根因说明：Deck 上 Clash TUN 的 fake-IP(198.18.0.x) 劫持 DNS，`codeload.github.com`
超时，但 archive.ubuntu.com / mirrors.aliyun.com 正常，因此走 apt 而非 GitHub 拉取。

## 二、命令与产物（已验证）

容器内（`podman exec`，非 root）：
  apt-get install -y vulkan-tools libvulkan-dev   # -> 1.3.275.0-1
  VK_LOADER_LAYERS_DISABLE="~implicit~" VK_DRIVER_FILES=/usr/share/vulkan/icd.d/radeon_icd.x86_64.json \
    vulkaninfo --json -o ~/native-recomp/logs/env22/vulkaninfo.json
  同上但 --text -> vulkaninfo.txt

踩坑：首次 `vulkaninfo --json`（无 -o，重定向 stdout）产出 **0 字节**。
  原因 = 隐式层 lsfg-vk-layer 报错写 stdout + DISPLAY 未透传。
  解法 = `-o <file>` 让工具自己写文件 + `--json`；成功。

## 四、两个对 M3 有实质影响的结论

### 4.1 ASTC 纹理：无硬件采样，但**不是阻断项**（已验证，源码+日志双证）
- 本机 GPU 不能直接采样 ASTC/ETC2（本轮 vulkaninfo + env23 宿主 vkprobe 双证）
- ScarletNX 自带 `astc.c`：用 **compute shader 解码到 RGBA8**
- 运行日志（env20/env21）确认走到该分支：
  `native ASTC textures were asked for, but the GPU can't sample ASTC: they are decoded to RGBA8`
- 影响（推断）：显存占用与首次加载时间上升（ASTC4x4 -> RGBA8 = 4 倍体积），
  但正确性不受影响。TOTK 大量使用 ASTC，需在 M3 关注 heap0 占用与着色器预热时长。
- Vulkan Video H.264 缺失 -> 过场视频走 CPU 解码路径（推断，待 M3 实测验证）

### 4.2 loader 版本差异：容器 1.3.275 < 宿主 1.4.350
-> 最终真机运行必须用**宿主 loader**，容器只用于构建与离线探测。
-> 已在 M1/env19 中体现：真机执行直接在宿主 `DISPLAY=:0` 下跑，不经容器。

## 附：勘误（2026-10-26 01:30 追加，原文不改）

§三 "Vulkan API：1.4.302（驱动侧）" 抄错。按 `VK_VERSION_*` 宏重解
`evidence/m0/env22-vulkaninfo.json` 的 `apiVersion=4211006`、`driverVersion=104865800`：
  - physical device apiVersion = **Vulkan 1.4.318**
  - driverVersion = **25.2.8**（与 `driverInfo="Mesa 25.2.8-0ubuntu0.24.04.4"` 一致）
注意：`apiVersion` 的 patch 位由 **loader 的 VK_HEADER_VERSION** 钳制，
因此 318 反映的是容器 loader/头版本，不是驱动能力上限。宿主机侧的对应值见 env23 附表勘误。
