## 2. 原生编译技术栈（ScarletNX 官方，BUILD.md 全文提取）

### 2.1 编译链

```
AArch64 游戏 NSO/NCA → 解析 → AArch64 指令
         ↓
  LLVM IR（IR a64.c / ir_simd.c / ir_fp.c / ir_codegen.c）
         ↓
  snx_ir_host（host detection）→ LLVM 为 host CPU 生成扩展
         ↓
  snx_recompile_from → LLVM codegen → LLVM IR 模块
         ↓
  link_elf.c / link_coff.c / link_macho.c（自建链接器）
  rtlib.c（共享运行时库）
         ↓
  模块 → <recompiled>/<id>/{ <id>_code.so, <id>_data/, <id>.ini, <id>.abi }
```

**关键事实**：
- **没有解释器**。无代码的 pc 排队到队首 → JIT 兜底编译；JIT 编不了 → 直接结束游戏并说明原因。
- **Build == Host == Target**：生成代码使用 host 扩展，运行时库由 LLVM 为每模块 CPU 编译，**运行时零检测** → 不可跨机搬运。
- **host 扩展**（x86 emitter）：AES-NI、PCLMULQDQ、SSE4.2 CRC32C、**VPTERNLOG**（BSL/BIT/BIF）、PAVGB/PAVGW、GF2P8AFFINEQB。
- **Chunks 批量**：`SNX_CHUNK_INSTRUCTIONS = 90000`（Android 20000）；CFG discovery 在平台中立 image view 上做。
- **两级编译**：静态 AOT + 运行时 JIT 兜底（`guest_jit.c` over `jit_service.c`）。

### 2.2 CMake 构建配置（Arch Linux / SteamOS 实际可跑）

```bash
# Arch Linux (SteamOS 基于 Arch):
sudo pacman -Syu --needed base-devel git cmake ninja clang llvm nasm perl pkgconf python3 sdl3

# CMake 选项:
cmake --preset default -B build
cmake --build build
# → build/{scarletnx, snx-shaderc}

# 可选裁剪:
# -DSNX_BUILD_NX=OFF       # 不要 Switch 运行时
# -DSNX_BUILD_GNUABI=OFF   # 不要 Linux AArch64 运行时
# -DSNX_BUILD_GUI=OFF      # 不要 GUI 启动器（headless 部署用）
# -DSNX_DEPLOY=OFF         # 不要运行时部署
# -DSNX_FFMPEG_ASM=OFF     # 去掉 NASM 汇编（更慢）
```

**依赖矩阵**：

| 依赖 | 用途 | 必须 | 来源 |
|---|---|---|---|
| **Clang / LLVM** | 代码生成（IR 转换） | ✅ | `clang` + `llvm`（Arch）/ `llvm-devel`（Debian） |
| **SDL3 ≥ 3.4** | 窗口、输入、音频 | ✅ | `sdl3`（Arch）；源码 fallback（CPM） |
| **FFmpeg** | NVDEC H.264/VP9 视频解码 | ✅ | CMake 自动构建 pinned release |
| **Vulkan ≥ 1.3** | 渲染后端（NVN→Vulkan） | ✅ | 系统 driver（RADV VANGOGH on Deck） |
| **OpenSSL** | 加密（hash/cipher/ssl service TLS） | ✅ | CMake 自动构建 pinned release |
| **NASM** | FFmpeg x86-64 汇编优化 | 可选 | `nasm`（Arch） |
| **Perl** | OpenSSL Configure | 可选 | `perl`（Arch） |

**AppImage 构建**（用于分发）：
```bash
# 在 Arch container 里用 quick-sharun：
scripts/linux-llvm.sh "$(uname -m)" ~/linux-llvm
cmake --preset default -B build/appimage \
  -DSNX_DEPLOY=OFF \
  -DCMAKE_INSTALL_PREFIX=/usr \
  -DLLVM_DIR="$HOME/linux-llvm/lib/cmake/llvm" \
  -DSNX_A64_DISASM=OFF
cmake --build build/appimage
cmake --install build/appimage
scripts/make-appimage.sh
# → dist/ScarletNX-linux-x86_64.AppImage
```
AppImage **静态链接 LLVM**；`linux-llvm.sh` 只构建 recompiler 需要的 libLLVM 目标。

### 2.3 产物部署结构

```
~/.local/share/scarletnx/
├── recompiled/
│   └── <title-id>/
│       ├── <title-id>                 # 可执行入口
│       ├── <title-id>_code.so         # 重编译 AOT 模块（无 imports，self-contained）
│       ├── <title-id>_data/
│       │   ├── control.nacp
│       │   ├── saves/                 # 存档
│       │   ├── mods/                  # Mod 目录
│       │   └── cheats/                # Cheat 目录
│       ├── <title-id>.ini             # source= (dump 路径), addons= (DLC)
│       ├── <title-id>.source          # 旧格式软链
│       └── <title-id>.abi             # 模块 ABI 印章（<16 hex>）
├── cache/
│   └── recompiled/
│       └── <title-id>/
│           └── <title-id>.jitcache    # JIT 编译缓存
└── settings.txt                       # 全局设置
```

**关键设计**：
- **`<id>_code.so` 无任何 imports**（self-contained shared object）
- **ABI 版本化**：`SNX_ABI` 当前 = 13；ABI 不匹配 → 运行时报错拒绝加载
- **`.jitcache` 验证**：guest code 逐字节相同 + 同 ABI + 同 LLVM/runtime lib + 同 host CPU + 同 settings
- **AOT Pack**：JIT 编译过的函数可打包进 AOT（`scarletnx -r game --jit-cache game.jitcache -O 2`），之后启动即全部 AOT

### 2.4 跨平台构建能力

| Build Host | Target Architecture | 产出格式 |
|---|---|---|
| Linux x86-64 | x86-64 ELF | `.so` 模块 + AppImage |
| Linux x86-64 (cross) | PowerPC64 ELF | ELFv1/v2（>32MiB stub） |
| macOS Arm64 | aarch64 Mach-O | dylib + ad-hoc 签名 |

## 3. 三条路径的转换方式

### 3.1 路径 A：ScarletNX（通用，推荐）

```
.xci / .nsp / .nxci / .dnsp（游戏容器）
  → hactool（内置 driver）→ ExeFS + RomFS 实时读取或提取
    → NSO 模块解析 → AArch64 指令
      → LLVM IR → AOT 静态重编译 → <id>_code.so（x86-64 ELF）
        → 运行时加载
          → NVN HLE（Switch GPU API 翻译）
            → Maxwell 命令缓冲区解码
              → Vulkan 绘制
                → RADV VANGOGH (Steam Deck GPU)
```

**转换特点**：
- **全 AOT 优先**：启动时编译全部已知函数
- **JIT 兜底**：运行时遇到未知函数即时编译（第一次慢，后续缓存）
- **AOT Pack**：玩一次后可将 JIT 缓存打包为永久 AOT
- **Mod/Cheat** 原生支持
- **更新/DLC** 通过 `addons=` 管理

### 3.2 路径 B：LAS Recomp（单游戏，最成熟体验）

```
exefs/romfs/（提取好的游戏目录）
  → gen.py（AArch64→C++ 翻译，capstone 5.0.9 disassembly + unicorn 解析跳转表）
    → generated/<module>.cpp（C++ 源码）
      → clang -O2 + lld → build/lasgame.so（x86-64 ELF shared lib）
        → 运行时链接 lasrecomp + lasgame.so
          → NVN-on-Vulkan 层（移植自 LAS Recomp）
            → Maxwell shader → SPIR-V（启动期或 warmup 编译）
              → Vulkan → RADV
```

**转换特点**：
- **AArch64 → C++ 翻译**（不同于 ScarletNX 的 LLVM IR 直接 codegen）
- **Zig 编译 C++**（玩家机器上的 start screen 用 Zig `zig cc`）
- **Capstone 5.0.9 精确版本**（其他版本 leave thousands 未处理）
- **Unicorn 2.1.4** 用于跳转表解析
- 启动期即时译码 + warmup.sh 预编译

### 3.3 路径 C：totk-recomp（TOTK 专用，Deck 优化）

```
TearsOfTheKingdom.xci + prod.keys
  → xci_carve.py + hactool 1.4.0 → 提取 NCA
    → nso.py（NSO 解压缩）+ funcs.py（找函数）
      → gen.py（AArch64→C++ 翻译）
        → mkninja_linux.py → ninja build
          → clang -O2 → build/totk-recomp（x86-64 ELF）
            → run.sh + Steam shortcuts
              → NVN-on-Vulkan（复用 LAS 代码）
                → warmup.sh（4.5 min）→ play
```

**转换特点**：
- **AArch64→C++**（同 LAS，但 TOTK 专用优化）
- **Ninja 构建系统**（替代 CMake）
- **Steam Deck 特化**：`TOTK_FPS` / `TOTK_UNLOCK_FPS` 环境变量
- **仅 v1.0.0**（build ID `082CE09B06E33A12`），其他版本不工作
- **build_from_xci.sh 一键打包**

## 4. GPU 转换路径（墙 B 的真实方案）

### 4.1 NVN → Maxwell → Vulkan 管线

```
游戏代码调用 NVN API (NVIDIA Vulkan-like SDK)
  → nvdrv (kernel driver 模拟)
    → GPFIFO ioctl → GPU command buffer
      → GPU thread 解码 Maxwell pushbuffer
        → 3D/MME/Compute/2D/DMA dispatch
          → Vulkan renderer (vk/)
            → shader: Maxwell SASS → SPIR-V (gpu/shader/)
              → vk/stream_incr → GPU execute
                → RADV (Mesa VANGOGH driver) → AMD GCN GPU
```

### 4.2 Maxwell Shader 处理

**ScarletNX**：
- 启动期 **离线译码全部** Maxwell SASS→SPIR-V（`prepare_shaders`）
- 输出 `<id>.vkshipped` 文件（预编译着色器库）
- 每帧绘制命中时直接读取缓存 → **运行时零译码延迟**
- ASTC 纹理：GPU compute shader 解码（`astc.comp`，GLSL，整数运算无浮点）
- Block Linear：`blocklinear.comp` + `texconv.comp`（两个 GPU shader）

**LAS/totk-recomp**：
- 首次运行即时编译
- warmup.sh 预跑完成（TOTK: 4.5 min / Deck）
- 其余在后台编译

### 4.3 MME (Macro Memory Engine) 原生优化

ScarletNX 已实现 **10 个 TOTK 高频 macro 原生执行**（`maxwell/mme_hle.c`）：
- Slots: 7, 8, 9, 12, 16, 27, 30, 35, 37, 38
- 通过 macro code hash 查表 → 原生实现 vs 解释器 fallback
- Eden 的 macro hash 表为参考基座

### 4.4 NVN 语义重放（已放弃方案）

官方已明确放弃 NVN API 调用重放：
- TotK 内联 NVN 调用（`BeginRecording` at `0x8714394` / `0x87164ac`）
- 65 depth 绘制在 GPFIFO 中而非记录列表
- Post-submit 观测太晚（Maxwell 已重写 guest memory）
- 会重复解码器（等于写了两遍 gpu.c + maxwell/）

**结论**：Maxwell decoder 保留为基座，优化方向是 native MME + 降低每 draw 成本。

## 5. GNUABI 运行时：Linux AArch64 二进制直接运行

ScarletNX 还有第三条路径：`scarletnx-gnuabi` — 把 AArch64 Linux 二进制直接在 x86-64 host 上跑：

```
AArch64 Linux ELF (静态/动态链接)
  → scarletnx-gnuabi 加载 ELF
    → LLVM IR → JIT 编译 (运行时逐函数)
      → Linux syscall 翻译 (syscall x8→x0-x5, 返回 -errno)
        → 宿主机 syscall
```

**实现范围**：
- ELF64 LE `EM_AARCH64` `ET_EXEC`/`ET_DYN`
- 全部文件描述符操作（read/write/openat/close/lseek/dup/fcntl/pipe2/ioctl）
- 元数据和目录操作（fstat/newfstatat/statx/readlinkat/getdents64/mkdirat/...）
- 内存操作（brk/mmap/munmap/mprotect）
- 进程管理（clone/fork, execve/wait4/kill/tgkill）
- 网络（host-backed sockets, poll/select, epoll, eventfd）
- `/proc` 虚拟节点、`/dev` 虚拟节点

**局限**：无 GPU/无显示/无声音，纯 CPU + 文件系统。可用于编译工具链（如 AArch64 GCC cross-compiler in sysroot）。

## 6. Steam Deck 原生部署方案

### 6.1 安装形态（排除 .deb）

SteamOS 是 **Arch Linux + pacman**，非 Debian/apt/dpkg。

| 方案 | 可行性 | 说明 |
|---|---|---|
| **AppImage** | ✅ 首选 | Deck 有 `libfuse3` + `setuid fusermount3` + `/dev/fuse`；`APPIMAGE_EXTRACT_AND_RUN=1` 兜底 |
| **纯目录 + run.sh** | ✅ totk 形态 | `run.sh` 加入 Steam "添加非 Steam 游戏" |
| **Flatpak** | ❌ 0 命中 | flathub 无匹配 |
| **.deb** | ❌ 不存在 | SteamOS 无 apt/dpkg |
| **pacman .pkg.tar.zst** | ⚠️ 理论可行 | `/` readonly 837MB，`/usr` readonly；需改 rootfs（破坏 SteamOS 完整性） |

### 6.2 Steam "添加非 Steam 游戏" 配置

```bash
# 假设部署到 /home/deck/apps/totk-recomp/
# 在 Steam 中：
# 游戏名称: Tears of the Kingdom (Recomp)
# 路径: /home/deck/apps/totk-recomp/run.sh
# 工作目录: /home/deck/apps/totk-recomp/
# 启动选项（可选）: TOTK_FPS=60 TOTK_UNLOCK_FPS=1

# 数据目录（自动）:
# ~/.local/share/totk-recomp/
# → saves/, settings/, shader cache/, extracted/
```

**纯新增可回滚**：
- Steam shortcuts.vdf 原本不存在（V1 验证）→ 纯新增文件
- 删除 `~/.local/share/<app>/` + 从 Steam 移除快捷方式 = 完全回滚
- AppImage 放置路径：`~/apps/<app>/` 或 `~/native-recomp/`

### 6.3 distrobox 构建路径（工具链不在 Deck 上）

**前提**：distrobox create 在 Deck 上有 CPU 死循环问题（V1 已证实）→ **推荐方案**：

1. **Mac 本机构建**（Apple Silicon）→ cross-compile 到 x86-64
2. **Linux PC 构建**（Ubuntu 24.04）→ 直接构建 → scp 到 Deck
3. **Deck 本地构建**（不推荐）：1-1.5h 编译时间 + distrobox 需先解决 overlay/fuse 根因

**Mac 本机构建 ScarletNX x86-64 AppImage**（BUILD.md § "Linux / FreeBSD → AppImage"）：
```bash
# Mac 需要：
# 1. Apple Silicon (M1/M2/M3/M4)
# 2. Xcode + brew install cmake ninja
# 3. 构建 x86-64 LLVM cross-codegen:
scripts/linux-llvm.sh x86_64 ~/linux-llvm-x64
# 4. clone + build:
cmake --preset default -B build/appimage \
  -DCMAKE_INSTALL_PREFIX=/usr \
  -DLLVM_DIR="$HOME/linux-llvm-x64/lib/cmake/llvm" \
  -DSNX_A64_DISASM=OFF \
  -DSNX_BUILD_NX=OFF     # 如果只想要 gnuabi
  -DSNX_BUILD_GNUABI=OFF # 如果只想要 Switch 运行时
cmake --build build/appimage
cmake --install build/appimage
# 5. 需要 podman + Arch container 做 AppImage 打包
```

## 7. 风险矩阵与已知缺口

### 7.1 已知缺口（官方声明）

| 缺口 | 严重程度 | 影响范围 | 备注 |
|---|---|---|---|
| **ARM FP NaN propagation / default-NaN** | 中 | FP 敏感游戏 | ScarletNX DIVERGENCES.md 确认 |
| **Directed FP rounding** | 中 | 同上 | — |
| **WFE 线程挂起** | 低 | 特定同步模式 | — |
| **32-bit 游戏（A32/Thumb）** | 高 | 3DS/早期的 Switch 游戏 | 仅合成程序测试过 |
| **真实游戏 Update/DLC** | 中 | 带 DLC 的游戏 | ScarletNX 支持；LAS/totk 不支持 |
| **Per-channel GPU scheduling** | 中 | 多线程渲染游戏 | 阻塞 channel 饿死 fence producer |
| **90° framebuffer rotation** | 低 | 竖屏游戏 | — |
| **Attachment feedback** | 低 | 特殊渲染技术 | — |
| **BCn texture fallback** | 低 | ASTC→BCn 转换 | — |

## 附录：与 iOS 移植的思路对比

| 维度 | iOS (Apple Silicon) | Steam Deck (Zen2 x86-64) |
|---|---|---|
| **ISA 匹配** | ✅ AArch64 → AArch64 (host==guest) | ❌ AArch64 → x86-64 (必须重编译) |
| **GPU 匹配** | ✅ Apple GPU → Metal (通过 MoltenVK) | ⚠️ Maxwell → Vulkan (需要模拟层) |
| **重编译必要性** | 不需要 (原生 ARM 二进制直接跑) | **必须** (LLVM AOT 或 AArch64→C++ 翻译) |
| **编译速度** | N/A | 17 min (PC clang) / 1-1.5h (Deck) |
| **跨机搬运** | 可以 (arm64 → arm64) | **不可以** (host CPU 绑定) |
| **Shader 处理** | MoltenVK 翻译 Metal → iOS GPU | Maxwell→SPIR-V 离线译码 |
| **存储格式** | iOS App (dylib + Mach-O) | Linux AppImage / 纯目录 |
| **安装方式** | TestFlight / 越狱 / App Store | Steam "添加非 Steam 游戏" |

## 11. ASTC 纹理 GPU 解码（ASTC.md 全文 19KB 提取）

### ASTC 解码管线

```
ASTC block → Block Linear deswizzle (blocklinear.comp)
  → ASTC compute shader (astc.comp, GLSL)
    → RGBA8 output (vk/astc.c staging buffer)
      → copy into UNORM/SGRB Vulkan image
```

**关键事实**：
- **GPU compute shader 解码**，非 CPU：workgroup 64 invocations 解码 64 blocks (两阶段)
- **纯整数运算，无浮点** → 输出不依赖 driver rounding
- 第一阶段：每 invocation 解码 1 block → shared memory (49 words/block, 9984 bytes)
- 第二阶段：64 invocations 各写 1 texel → coalesced stores, no branch per texel
- 性能（lavapipe, 4096x4096）：4x4=111ms, 6x6=87ms, 8x8=79ms, 12x12=77ms
- **无 CPU fallback**：pipeline 创建失败是致命的

### Block Linear deswizzle (BLOCKLINEAR.md 全文提取)

```
Guest Block Linear layout → staging buffer (vk/blocklinear.c)
  → GPU shader 转换 → Vulkan linear rows (vk/texconv.comp)
```

**关键设计**：
- **CPU 只拷贝**：guest staging → host staging → guest memory，**从不读 GPU 内存做转换**
- 两个方向同一 shader：push constant 选方向，uniform per 16 bytes
- 2 shaders 替代 20 pipelines → 启动期减少编译时间
- 所有整数运算，字节到字节精确
- 大 texture 分 strip/band 处理（band=64MiB 或 allocation cap）

### NVN Format 映射表（NVN_HLE.md 全文提取）

## 14. GPU-Owned Guest Memory（GPU_OWNERSHIP.md 全文提取）

### 核心概念

游戏 GPU 操作（NVDEC 输出、VIC 合成、DMA 复制、2D 引擎）的结果驻留在 GPU 内存中。当重编译的 guest CPU 代码访问这些区域时，需要**将 GPU 数据写回 guest memory**。

### Trap 模型

```
GPU 操作结果 → GPU-owned memory range
  ↓
Guest CPU 读/写触发 trap
  ↓
Handler 从 GPU 数据写回 mirror → 解除 trap → range 回到 CPU 拥有
```

三个级别：none / write-only / read-write。

### Linux 实现（userfaultfd）

- `userfaultfd` minor faults + shmem alias pool
- 5.13+ minor faults on shmem, 5.11+ user mode only
- Debian 13 (6.12) 满足所有要求
- 旧内核 fallback: `mprotect` + signal handler（Skyline 形状）
- **Deadlock 预防**：trap lock 不在 Vulkan 调用/guest memory 访问/wait 期间持有

### 各平台实现

| Platform | Mechanism |
|---|---|
| Linux | userfaultfd + shmem alias pool (5.13+) |
| Windows | VirtualProtect(PAGE_NOACCESS) + vectored exception handler |
| macOS | Mach exception ports + mach_vm_remap |
| 无支持 | GPU 结果直接 copyback（慢但正确） |

### 5 个 Phase 状态

- **Phase 1-4** (Linux): ✅ Done
  - Trap layer + map (Linux)
  - GPU consumers (texture uploads, render target loads, vi present, VIC inputs)
  - NVDEC + VIC: GPU-owned surfaces (NV12 block linear)
  - DMA engine + 2D blit: GPU copy 替代 CPU loops
- **Phase 5** (Windows/macOS): 进行中
- **Inline-to-memory**: 保持 CPU 写（pushbuffer 数据由 GPU 读）

### Deck 影响

- SteamOS 6.12+ → userfaultfd 完整支持 ✅
- **GPU-owned memory 机制对 Deck 部署无额外风险**

## 19. 手柄映射：如何高度匹配 Switch 按键布局（第 7 轮新增）

> 取证范围：ScarletNX `src/common/utilities/pad_map.{c,h}`、`pad_sdl.{c,h}`、`src/nx/runtime/platform/gamepad.{c,h}`；
> totk-recomp `runtime/hle_hid.cpp`(93.9KB)；LAS Recomp `runtime/hle/input.c`(44KB)、`runtime/hle/bindings.c`、
> `runtime/input_bind.h`、`runtime/nvn/texpatch.{c,h}`；SDL3 `src/joystick/SDL_gamepad.c`、
> `src/joystick/controller_list.h`、`src/joystick/hidapi/SDL_hidapi_steamdeck.c`。
> 全部为**上游源码原文**（`已验证-源码级`），非二手描述。

### 19.1 三家共同的第一原则：绝不按 XInput 语义硬编码

三家都只用 SDL 的**位置语义**（SOUTH/EAST/WEST/NORTH = 下/右/上/左）取按键，从不假设"button 0 = A"：

| 实现 | 取值方式 | 关键代码事实 |
|---|---|---|
| ScarletNX | `pad_sdl.c` 固定表 `BUTTONS[] = {SOUTH, EAST, WEST, NORTH, LEFT_SHOULDER, RIGHT_SHOULDER, …}`，再经 `pad_map` 翻译成主机按钮位 | `snx_pad_of_button()` / `snx_pad_held()`；LT/RT 不走 button 走 axis + `SNX_PAD_TRIGGER` 阈值 |
| totk-recomp | **先按丝印标签**（`SDL_GAMEPAD_BUTTON_LABEL_A → BtnA`…），无标签才退回位置映射（EAST→A、SOUTH→B、NORTH→X、WEST→Y） | `hle_hid.cpp` 内注释明确此优先级 |
| LAS Recomp | 16 个 Switch 输入（`BTN_A…BTN_DOWN`，**编号即 nn::hid 的 button bit**）→ 每槽一个可重绑的宿主按键 `g_bind_pad[]` | `input_bind.h` 有 `_Static_assert(BTN_DOWN == BIND_DOWN && BTN_ZL == BIND_ZL)` 锁死"绑定顺序 == 主机 bit 顺序" |

SDL3 侧的判定依据（`SDL_gamepad.c`）：`SDL_GetGamepadButtonLabelForType()` → `GetGamepadFaceStyleForGamepadType()`，把机型归成四种"面孔风格"，其中
`NINTENDO_SWITCH_PRO / JOYCON_LEFT / JOYCON_RIGHT / JOYCON_PAIR → FACE_STYLE_BAYX`（B 在下）、Xbox/默认 → `ABXY`（A 在下）、PS → `SONY`、GameCube → `AXBY`。
mapping 里还能带 `hint:!SDL_GAMECONTROLLER_USE_BUTTON_LABELS:=1` 强制按丝印解释。
**结论：只要用 SDL3，"这只手柄的 A 到底在哪"是 SDL 已经替你判好的既有事实，不需要自研机型表。**

### 19.2 Steam Deck 内置手柄在这一套机制下的实际归属（决定性结论）

| 事实 | 证据 | 影响 |
|---|---|---|
| Deck 内置控制器 VID:PID = `28de:1205` → `k_eControllerType_SteamControllerNeptune` | `controller_list.h:669` | SDL 认识它，不是 unknown |
| Steam Input 生效时暴露的是 `28de:11ff` → `k_eControllerType_UnknownNonSteamController`（"Steam Virtual Gamepad"） | `controller_list.h:665`；SDL #9148 逐字复现 SDL2=`0x1205` / SDL3=`0x11ff` | 机型退化 → 面孔风格落 `default: ABXY` |
| 两种归属下面孔风格都是 **ABXY（A 在右、B 在下）** | `SDL_GetGamepadFaceStyleForGamepadType` 的 `default` 分支 | **与 Switch 物理布局完全一致，本来就不需要 A/B 交换** |
| ScarletNX `snx_pad_symmetric()` 只对 PS3/PS4/PS5 返回 1（摇杆并排），Deck 返回 0 | `pad_sdl.c` | Deck 是**非对称摇杆**，与 Switch 同构 → 摇杆布局零适配 |
| ScarletNX 默认映射 `POSITION = {1,0,3,2,…}`，注释 "A right, B bottom, X top, Y left" | `pad_map.c:15-16` | **默认值就是任天堂布局**；`swap_a_b` 是给 Xbox 布局手柄准备的，Deck 应保持关闭 |
| Deck 多出的 5 个键 SDL 有专用枚举：`STEAM_DECK_QAM / LEFT_PADDLE1/2 / RIGHT_PADDLE1/2 / LEFT_TOUCHPAD / RIGHT_TOUCHPAD` | `SDL_hidapi_steamdeck.c:37-43` | QAM/Steam 键可当"呼出覆盖层"，背键 1/2 是 **ZL/ZR 的最佳落点候选** |

→ **对本目标最重要的一句话**：Deck 手柄到 Switch 的映射不是"重映射问题"，而是"同一布局的两个厂商实现"。真正需要适配的只有两件事：① L3/R3 vs Switch 无此键、② ZL/ZR 在 Deck 上是 L2/R2 模拟扳机（LAS 为此专门造了 `PADB_LTRIGGER=26 / PADB_RTRIGGER` 把模拟轴当按钮绑定）。

### 19.3 三家的可配置面（决定"能不能自定义到手感满意"）

- **ScarletNX（可配置面最全，8 玩家槽）**：`gamepad.h:12` `SNX_GAMEPADS 8`（"one slot for each guest Npad player"）；.ini 键 `gamepad_p<N>_controller`(GUID，`"/2"` 表示同型号第二只)、`player_connected`、`player_type`(PadKind)、`player_swap_a_b`、`player_vibration`、`player_button_map`；全局 `swap_a_b / stick_dead_zone / vibration / background_input / pair_joy_cons / button_map`。映射有**人类可读 .ini 文本格式**（`pad_map.c` 的 `south:B east:A …`，`snx_pad_map_read/write` 双向），并有 `gamepad_store_player_map()` 写回。UI 页名 `"Controllers" / "Button map" / "Player"`；非法词不改动原映射并回显（`say_map_kept`）。另有 SDL 映射数据库加载：支持 `SDL_GAMECONTROLLERCONFIG_FILE` 环境变量覆盖 + 启动器同目录 `gamecontrollerdb.txt`（未识别手柄可自助加 mapping，日志会直接提示"add one to gamecontrollerdb.txt"）。
- **LAS Recomp（体验最完整：含"按键提示贴图"重绘）**：游戏内 Controls 页 + 开始界面可"点一项→按下键"捕获（`bind_capture_begin/_event`，5s 超时、**冲突自动交换两个输入**、可单项/全量复位），落盘 `larecomp.ini` 的 `bind_pad_<input>` / `bind_key_<input>`（只写非默认项）。**独有**：`runtime/nvn/texpatch.c`(65KB) 在**纹理上传时**按内容哈希识别游戏自带 UI 贴图并重绘成 Xbox/PlayStation 按键图标（`texpatch_apply()`，`texpatch_generation()` 触发重传），由 `bind_prompt_host(slot)` 把"当前驱动 Switch 输入 X 的宿主键"反馈给贴图选择 → **屏幕提示跟着你的真实手柄丝印走，而不是显示游戏画死的 Switch A/B**。 Nintendo 外观时 `texpatch_apply` 是 no-op（零副作用）。
- **totk-recomp**：标签优先 + 位置兜底，无 per-player 配置面（面向单游戏单玩家的 recomp 定位）。

### 19.4 Deck 落地建议（把上面变成 SOP）

1. **不要开 A/B 交换**。Deck 与 Switch 同为 A-右 / B-下；ScarletNX 默认即正确，LAS 的 family=0(Nintendo) 或 1(Xbox) 都不会改变这一点（只影响提示图标）。
2. **背键当 ZL/ZR**（V5 首要自定义项）：Deck 的 paddle1/2 在 SDL 直连路径下是独立 button（`SDL_GAMEPAD_BUTTON_STEAM_DECK_*_PADDLE1/2`），LAS 可用 Controls 页把它绑到 `BIND_ZL/BIND_ZR`；走 Steam Input 路径则由 Steam 层把背键映射成 L4/L5 或直接 ZL/ZR。**优先 SDL 直连**，因为 §20 的体感要求同一条路径。
3. **未识别手柄（第三方 Pro 手柄）自助加 mapping**：ScarletNX 与 LAS 都读 `gamecontrollerdb.txt`（ScarletNX 可 `SDL_GAMECONTROLLERCONFIG_FILE` 覆盖路径；LAS 日志 `[input] gamecontrollerdb.txt: %d controller mapping(s) added`）；ScarletNX 日志会打印 GUID 供抄写。
4. **提示图标一致性（LAS 路线）**：Deck 内置手柄的机型判定链是 `28de:1205 → SteamControllerNeptune → face style default=ABXY → SOUTH 标签 = A` → `input_family_of_type()` 落到 `default: return 1`（按 Xbox 图标提示）。**注意 Deck 手柄丝印只有图标没有字母，所以"ABXY"是 SDL 的保守归类，不是 Valve 的官方语义**。想让游戏继续显示 Switch 的 A/B/X/Y 图标（与 Deck 物理布局反而一致），用设置项 **"Button icons" = Nintendo**（`g_settings.prompts` 的 `PROMPTS_NINTENDO`，同时统一菜单布局 family）；`LARECOMP_PAD_TYPE=nintendo` 是**测试用途**的假装手柄接入，不作为部署手段。

### 20.1 三家实现的运动传感完成度（先给结论）

| 实现 | 六轴状态 | 关键实现细节 |
|---|---|---|
| **ScarletNX** | ✅ **完整**（含左右分离） | SDL 传感器 API 开 `SDL_SENSOR_ACCEL/GYRO` 及 `_L/_R`（`enable_motion`，无传感器打日志 `exposes no motion sensors through SDL`）；单位换算 `acc = (-a[0], a[2], -a[1]) / 9.80665`（SDL m/s² → Horizon g）；`hid_motion.c` 把 acc+gyro 积分成四元数（scalar-first）→ 输出 Horizon 的 3×3 direction matrix；重力初始化 pitch/roll、静止时缓修 gyro 漂移、**yaw 无重力参考**；`hid_motion_at_rest()` 阈值 \|acc\|²∈(0.85,1.15) 且 \|rate\|²<0.0025 |

### 20.2 Deck 内置 IMU 的四条取数路径（含可行性判定）

| # | 路径 | 机制 | 判定 |
|---|---|---|---|
| **A** | **SDL3 内置 hidapi_steamdeck 驱动** | SDL **已实现**：`SDL_hidapi_steamdeck.c:250-258` 解析 64B 输入报告里的 `sGyroX/Y/Z`、`sAccelX/Y/Z`，量程 ±2000 dps、±2 g，轴换序 (x,z,−y)，并 `SDL_PrivateJoystickAddSensor(GYRO/ACCEL)`；`SetSensorsEnabled` 注释 "On steam deck, sensors are enabled by default. Nothing to do here." | **条件可用**。硬前提：设备要以 `28de:1205`(SteamControllerNeptune) 出现。#9148 实测：Steam 在跑时 SDL3 看到的是 `28de:11ff`(Steam Virtual Gamepad)，机型退化 → 驱动不接管，**gyro 与背键全部丢失**（rumble 正常）。该 issue 被 slouken 以 "unplanned / 请用 Steam Input" 关闭，**问题本身未修** |
| **B** | **SteamDeckGyroDSU（cemuhook DSU over UDP）** | Deck 侧常驻进程用 HIDAPI 打开 `28de:1205` **interface 2**、64 B 报告、4 ms 周期，先写 feature report（`0x00 0x87 0x0f 0x30 0x18 …`）启用 IMU；换算常量 `ACC_1G=0x4000`、`GYRO_1DEGPERSEC=16`、`GYRO_DEADZONE=8`、加速度平滑 `ACCEL_SMOOTH=0x1FF`(0.95/0.05 低通)；以 **DSU 协议**（magic `DSUS`，UDP **26760**）只发 `MotionData`（6 轴 float + 时间戳），**按钮/轴不发** | **当前最可用**。以 `systemctl --user enable --now sdgyrodsu.service` 安装（`~/sdgyrodsu/` + `~/.config/systemd/user/`），纯 home 目录、无 root、可完全卸载 → 与 Deck 只读 rootfs 兼容。代价：多一个进程 + 一次 UDP 往返 + 一层平滑（延迟来源，V5 要实测）；仓库最后推送 2024-03-28（v2.1，已 2.5 年未更新，需自验可用性） |
| **C** | **Steam Input 把 gyro 映射成鼠标** | Steam 层转换 | **不可用**。原生气体读的是 IMU 样本，鼠标位移无法还原为 acc/gyro；且 §18 的 #347（Gaming Mode 从 Steam 内启动 B 键双输入）同源风险 |
| **D** | **自定义内核驱动** | #9148 里驱动作者 mmmaisel 的原型：给 `hid-steam` 加 sysfs 开关以绕过"打开 hidraw 即隐藏经典 gamepad 接口"的内核 quirk，使多程序共享 | **不可用于 SteamOS**（需自编译内核，与只读 rootfs/OTA 冲突）。记录以备将来 |

**关键补充事实（决定了 A/D 之外的第五条捷径）**：#9148 讨论确认 ① Linux 上 hidraw **允许多程序同时打开**（作者已更正早期相反结论）；② Deck 内核有"hidraw 被打开即隐藏经典 gamepad 接口"的 quirk；③ SDL3 自 #8125 起已支持经**内核**接口取运动传感器（SDL2 不支持）。

### 21.2 参考实现的完整数据模型（取自 Ryujinx 源码，可直接照搬）

取证仓库：`NextendoNetwork/Ryujinx-Nextendo`（活跃维护的 Ryujinx 分支，pushed 2026-10-23，`main` 分支 4551 blob，NFC 子系统 51 个文件）。

**标签本体**
- 物理卡 = **NTAG215**；dump 文件 = **540 字节**（`AmiiboDump`：`if (dumpData.Length < 540) throw`）。
- 加密区：`data[0x014:0x034]` + `data[0x0A0:0x208]`（共 `0x188` 字节）做 AES-CTR；HMAC 覆盖 `[0x000:0x008] + [0x011:0x034] + [0x054:0x080] + [0x0A0:0x208]`；`data[0x034:0x054]` 存 32 B tag HMAC。**注意 page 0x11 的 2 字节、page 0x20-0x28 会参与 key-derived seed 校验** → 不能只塞应用区就假装是真卡。
- 主密钥：`key_retail.bin` **160 字节** = 两半 80 B（DataKey / TagKey），每半拆为 `HmacKey 16 + TypeString 14 + Rfu 1 + MagicSize 1 + MagicBytes 16 + XorPad 32`。

**运行时被游戏读到的东西**（这才是"虚拟刷"真正要喂的）
- 状态机 `NfpDeviceState`：`Initialized 0 → SearchingForTag 1 → TagFound 2 → TagRemoved 3 → TagMounted 4`（`Unavailable 5 / Finalized 6`）。`INfp.cs` 的命令-状态联动是硬约束：`StartDetection`→置 SearchingForTag；只有 `TagMounted`（部分命令 `TagFound` 亦可）才允许 `OpenApplicationArea/GetApplicationArea/SetApplicationArea/GetTagInfo`；`RemoveTag` 把 TagMounted 退回 TagFound。**必须挂 `AttachActivateEvent` 的事件句柄**，游戏是等事件而不是轮询。
- `GetTagInfo` → `TagInfo{ UuidLength, Uuid[10] }`（`AmiiboConstants.UuidMaxLength = 10`，实际 UUID 9 字节 + BCC：`uuid[3]=0x88^u0^u1^u2`、`uuid[8]=u3^u4^u5^u6`，且**同一 amiiboId 要持久复用同一 UUID**，否则游戏认为是另一张卡）。
- `GetCommonInfo` → `LastWriteYear/Month/Day`、`WriteCounter`、`Version=1`、`ApplicationAreaSize = 0xD8`（应用区固定 **216 字节**）。
- `GetRegisterInfo` → Mii(`CharInfo`) + **Amiibo 昵称** + 首写日期。
-- `GetModelInfo` → modelNumber/modelName/amiiboId。**目录数据来自 The Amiibo API**（`src/Ryujinx/Common/Models/Amiibo/AmiiboApi.cs` + `AmiiboApiGamesSwitch.cs` + `AmiiboApiUsage.cs`，即 amiibo.com 的 `Amiibo.json` 远端清单，含 series/name/number/机型/可用玩法）；仓库里的 `assets/Locales/Amiibo.json` 只是 UI 文案本地化，不是目录。离线场景需自备缓存清单或让用户手填 amiiboId。
- 落盘形态 `VirtualAmiiboFile{ FileVersion, TagUuid, AmiiboId, NickName, FirstWriteDate, LastWriteDate, WriteCounter, ApplicationAreas[{ApplicationAreaId, byte[]}] }` → **每个 Amiibo 一份持久 NV 存储**。

### 21.3 三条实现路线对比（Deck 无 NFC 硬件）

| 路线 | 做法 | 评价 |
|---|---|---|
| **S：纯软件注入**（推荐） | 在 `nfp:user` handler 里做虚拟标签：热键触发 → DeviceState 推到 TagFound → 喂 TagUuid/CommonInfo/RegisterInfo/ApplicationArea → 触发 ActivateEvent。库文件用 `.amiibo`/`.bin` + 每卡 JSON 持久区 | **唯一与"原生运行"完全契合**、零外设、正合"需要用的时候虚拟刷"。TOTK 尤其合适：Amiibo 只出**每日奖励宝箱**，靠 `LastWriteDate/WriteCounter` 限次，软件实现反而比实体卡更好管（可改日期刷次） |
| **H1：USB/BT 读写器**（PN532 / ACR122U） | 走 hidraw 或 libnfc，读实体卡原始 540 B 再解出应用区 | Deck 需 USB-C hub；ACR122U 是标准 HID，`uaccess` 已够（env14 证实 deck 用户有 hidraw ACL）；PN532-USB 权限面更麻烦。**致命点：读出的是加密区，仍要 `key_retail.bin` 才能拿到应用区** → 硬件并不降低对主密钥的依赖，只增加实卡成本 |
| **H2：硬件仿真标签**（Flipper Zero / AmiiBee / N2-Elite / PIXL、手机写 NTAG215：CattleGrid、Amiibomb） | 由硬件**冒充**一张 NTAG215 | **对原生 recomp 无效**：游戏读的是 `nfp:user` IPC，不是真射频场；除非 recomp 自己实现 NFC 透传后端（三家都没有）。这条路线只在"用真机/真读卡器"语境成立 |

**必须讲清的一条红线**：不管走 S 还是 H1，从 dump 里解出应用区都要 `key_retail.bin`（任天堂主密钥）。所以"只备份我自己的实体 Amiibo"在技术路径上无法与批量解密分离——这一点不粉饰。可完全避开主密钥的子集是：**只用应用区已知为空的场合（首次接触、只读 ModelInfo 换外观/图鉴）或自建应用区内容**，此时虚拟标签不需要任何密钥。

### 21.4 工作量与顺序（若批准实现）

1. 状态机 + 事件句柄 + `GetDeviceState`（让游戏认为"NFC 可用"，先别给数据）→ 验收：游戏不再报"无法读取 Amiibo"，且不会卡在 SearchingForTag。
2. `GetTagInfo/GetCommonInfo/GetRegisterInfo/GetModelInfo` 固定假数据 → 验收：游戏能显示一次刷入并给奖励。
3. `OpenApplicationArea/GetApplicationArea/SetApplicationArea` + 每卡持久 JSON（照抄 `VirtualAmiiboFile` 字段）→ 验收：**跨会话数据保留**（TOTK 存读档后宝箱/自定义造型仍在）。
4. 接 `.amiibo`/`.bin` 导入 + 目录 UI（可复用 ScarletNX 的 `pad_menu` 页机制），并做"每日限次"策略开关。
5. 密钥处理：`key_retail.bin` 由用户自备、路径写在配置里、不落仓库、不入日志；无密钥时降级为"空应用区模式"。

### 21.5 补：ScarletNX 已声明的 NFC 命令全清单（逐行核对 misc.swipc:184-243）

- `nfp:user` / `nfc:user` 各只有一个入口命令 `[0] CreateUserInterface()`，真正的接口是返回的 `nn::nfp::detail::IUser` / `nn::nfc::detail::IUser`。
- **`nn::nfp::detail::IUser` 共 29 个命令**：`Initialize Finalize ListDevices StartDetection StopDetection Mount Unmount OpenApplicationArea GetApplicationArea SetApplicationArea Flush Restore CreateApplicationArea GetTagInfo GetRegisterInfo GetCommonInfo GetModelInfo AttachActivateEvent AttachDeactivateEvent GetState GetDeviceState GetNpadId GetApplicationAreaSize AttachAvailabilityChangeEvent RecreateApplicationArea StartDetectionWithFilter InitializeOld FinalizeOld GetStateOld IsNfcEnabledOld`
- `nn::nfc::detail::IUser`：`Initialize Finalize GetState IsNfcEnabled ListDevices`（+ `StartDetection/StopDetection/GetTagInfo/AttachActivateEvent/AttachDeactivateEvent/GetDeviceState/GetNpadId/AttachAvailabilityChangeEvent` 等 405-412 段）。
- 结构体宽度已在同一文件写死：`TagInfo = bytes<0x58>`、`RegisterInfo = bytes<0x100>`、`CommonInfo = bytes<0x40>`、`ModelInfo = bytes<0x40>`，`nn::nfc::DeviceHandle = bytes<8,4>`。
- **实现含义**：IPC 编解码、参数宽度、命令号全部已由上游 .swipc 定义并生成，自研后端只需填语义（状态机 + 数据源），**不需要逆向 NFC 协议**——这是"虚拟刷"成本远低于直觉的根本原因。
