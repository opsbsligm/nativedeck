## 1. 作战路线图

### Phase 1 — 环境验证（V1）🔒 纯新增，零风险
**目标**：在 Deck 上验证上游发布物能启动，建立"环境侧"可信基线。不碰游戏数据。

| 步骤 | 命令（Deck） | 时间 | 判定 |
|------|-------------|------|------|
| 1.1 | `mkdir -p ~/native-recomp && cd ~/native-recomp` | — | 目录创建 |
| 1.2 | 拉 ScarletNX: `curl -LO https://github.com/scarletnx/nightly/releases/latest/download/ScarletNX-linux-x86_64.AppImage` | 5s | 47.3MB 下载 |
| 1.3 | 拉 LAS: `curl -LO https://github.com/peiikai/LASRecomp/releases/download/beta_5.1/LAS.Recomp-beta_5.1-linux-x86_64.AppImage` | 5s | 112MB 下载 |
| 1.4 | `chmod +x *.AppImage` | <1s | 权限 |
| 1.5 | `./ScarletNX-linux-x86_64.AppImage --version` | 2s | 列出驱动/渲染后端 |
| 1.6 | `./LAS.Recomp-beta_5.1-linux-x86_64.AppImage --help` | 5s | 列出可执行游戏 + 渲染驱动 |
| 1.7 | 若 1.5/1.6 失败 → `APPIMAGE_EXTRACT_AND_RUN=1 ./ScarletNX-linux-x86_64.AppImage --version` | 5s | 兜底 |
| 1.8 | `APPIMAGE_EXTRACT_AND_RUN=1 ./LAS.Recomp-beta_5.1-linux-x86_64.AppImage --help` | 5s | 兜底 |

**判定标准**：两个 AppImage 均能 `--version`/`--help` 并输出一行驱动列表 → V1 通过。  
**失败判定**：两者均返回段错误 → V1 阻断，需排查 FUSE/libc 版本。

**回滚**：`rm -rf ~/native-recomp`。

### Phase 3 — 首个原生运行（V2）🔴 需游戏资产
**前提**：游戏 dump（`.xci`/`.nsp`）+ `prod.keys` 就位。

| 步骤 | 命令 | 时间 |
|------|------|------|
| 3.1 | **桌面模式**：将 AppImage 拷到 Deck（scp 或浏览器下载） | — |
| 3.2 | 首次运行 LAS beta_5.1：首次启动多花数分钟（prepare），然后 `./LAS.Recomp-beta_5.1-linux-x86_64.AppImage path/to/游戏.dump prod.keys` | 5-15 分钟准备 |
| 3.3 | **记录帧率/温度/时长**：`MANGOHUD=1 %command%` 或 `/usr/bin/mangohud %command%` 在 Steam shortcut 中设置 | 运行时 |
| 3.4 | **首次着色器编译**：LAS beta_5+ 会离线编译 Maxwell 着色器为 SPIR-V（245MB~2GB），需耐心等待，不杀进程 | 视游戏规模 5-30 分钟 |
| 3.5 | **实跑 15 分钟**：连续运行含至少 3 次场景切换 + 2 次镜头旋转，记录 fps/冻结/temperature | 15 分钟 |

**判定标准**：能进场景、帧率可接受（≥30fps 野外 / ≥20fps 城市场景）、无冻结/崩溃 → V2 通过。  
**失败判定**：段错误、device lost、<10fps、着色器编译死锁 → 记录错误日志到 `~/.local/share/lasrecomp/log.txt`，分析根因。

**回滚**：`rm -rf ~/.local/share/lasrecomp ~/native-recomp`。

### Phase 4 — ScarletNX 重编译 + 压力测试（V3）
**目标**：用 ScarletNX 重编译同一款游戏，对比性能；30 分钟长跑验证 BAR/显存预算风险。

| 步骤 | 命令 | 时间 |
|------|------|------|
| 4.1 | `./ScarletNX-linux-x86_64.AppImage path/to/游戏.dump prod.keys --output=recompiled/game/` | 视规模 10-30 分钟 |
| 4.2 | `./recompiled/game/ScarletNX-linux-x86_64.AppImage --game=recompiled/game/` | 运行时 |
| 4.3 | **MangoHud 持续记录**：fps、GPU busy%、device-lost 计数 | 运行时 |
| 4.4 | **30 分钟长跑**：场景切换 + 镜头旋转 + 战斗/交互；记录 `vi:` 缺页日志 | 30 分钟 |
| 4.5 | **对比分析**：LAS vs ScarletNX 帧率/显存/稳定性差异 | 完成后 |

**关注指标**：
- FPS 曲线（前 5 分钟、10 分钟、30 分钟段分别均值）
- GPU busy%（`vkEnumeratePhysicalDeviceMemoryProperties` + `VK_EXT_pipeline_statistics`）
- Device lost 次数（dmesg 中 `amdgpu` 相关行）
- `vi:` 缺页触发计数（LAS issue 中记录的关键指标）

### V5 — 手柄映射 + 体感链路（**根因级，优先级最高**）

| 步 | 动作（Deck 侧） | 判据 |
|---|---|---|
| 5.1 | Desktop Mode 跑 SDL3 `testgamecontroller`（AppImage 内置或 distrobox 内），分别记录 **Steam 运行时**与 `steam-runtime-quit` 后两种状态 | 设备 VID:PID 是 `28de:1205` 还是 `28de:11ff`；`SDL_GamepadHasSensor(GYRO/ACCEL)` 真/假；背键 `paddle1/2` 有无事件 → **一次判定路径 A 是否可用** |
| 5.2 | 若 5.1 失败：在 Gaming Mode 的控制器设置里把"陀螺仪"设为 **None**（让原始设备透传），重复 5.1 | 由假变真 → 说明是 Steam Input 吞传感器，走"透传"配置即可，无需 DSU |
| 5.3 | 仍失败：安装 `sdgyrodsu`（`~/sdgyrodsu/` + user systemd，纯 home、无 root），`nc -u -l 26760 \| xxd \| head` 抓包 | 收到 `DSUS` 魔数包 → 路径 B 成立；同时记录静止噪声 |
| 5.4 | 端到端：recomp 内 `hid_motion_at_rest()` 判静止、平放朝上时四元数≈恒等、`accel.z` 符号符合各自约定（totk: −1） | 无"右向恒定漂移"（totk 注释里的历史 bug）、40 s yaw 漂移 < 10° |
| 5.5 | 映射验收：**不开** A/B 交换，逐项按 A/B/X/Y/L/R/ZL/ZR/+/-/方向键；背键绑 ZL/ZR | 16 个 Switch 按钮全对位、无双输入（规避 LAS #347 型冲突）、摇杆方向正确 |
| 5.6 | 延迟实测（可选）：手机 240fps 慢镜头同时对拍 Deck 与 Switch 手柄的同一动作 | 给出 DSU 路径的端到端延迟量级（估计 15–40 ms，未验证） |

**时间**：5.1–5.2 十分钟；加 5.3–5.5 约 40 分钟；5.6 另计 15 分钟。
**零写入方案**：5.1/5.2 纯运行与设置读取；5.3 需写 `~/sdgyrodsu` 与 `~/.config/systemd/user/`（可 `systemctl --user disable` + 删两处分文件完全回滚）。
